## 一、项目概述

### 1.1 业务背景

客户(服装品牌方)原有旧版网站系统存在三方面问题:

1. **无运营能力:** 商品为静态页面,上架需改代码,业务人员无法自主维护;
2. **无移动端:** 缺乏微信生态内的展示入口(H5/小程序),与客户触达渠道单一;
3. **无扩展性:** 数据陈旧、结构混乱,无法支撑双语展示与业务扩展(色卡、定制、新品等场景)。

### 1.2 建设目标

| 目标 | 说明 |
| --- | --- |
| 三端触达 | PC 官网 + H5 手机端(微信内打开即用)+ 微信小程序,覆盖主流访问场景 |
| 自主运营 | 非技术运营人员通过后台自助上架商品、维护风格/色卡/轮播图 |
| 双语展示 | 面向海外客户,全站中英双语(前端文案 + 数据内容双语) |
| 低成本部署 | 在 2 核 4GB 云服务器稳定运行,支撑上千商品、4GB+ 图片规模 |

### 1.3 交付成果(规模)

| 维度 | 数量 |
| --- | --- |
| 交付端数 | 3 端(PC 后台 / H5 / 小程序)+ 1 套后端服务 |
| 页面规模 | H5 8 页 · 小程序 8 页 · 后台 7 个功能菜单 |
| 后端接口 | 前台 6 个控制器 + 后台 11 个控制器 |
| 数据库 | 7 张核心业务表,全表逻辑删除 + 双语字段设计 |
| 上线状态 | 已正式上线运营,持续迭代中 |

## 二、整体架构设计

### 2.1 架构总览

```
                        ┌─────────────────────────────┐
                        │         Nginx 反向代理        │
                        │      (静态资源 + /api 转发)     │
                        └──────┬──────────┬───────────┘
                               │          │
              ┌────────────────┘          └────────────────┐
              │                                            │
   ┌──────────▼──────────┐                    ┌───────────▼──────────┐
   │  H5 手机端 (Vue3)    │                    │  PC 管理后台 (Vue3)   │
   │  响应式·手机/PC双形态  │                    │  Element Plus + JWT  │
   └──────────┬──────────┘                    └───────────┬──────────┘
              │                                            │
              └───────────────┬────────────────────────────┘
                              │  HTTP / JSON
                   ┌──────────▼──────────────────────────┐
                   │   Spring Boot 3 后端                 │
                   │  /api/v1/** 前台 · /api/admin/** 后台  │
                   │  Redis 缓存 · 百度翻译 · 图片压缩       │
                   └──────────┬──────────────────────────┘
                              │
                   ┌──────────▼──────────────────────────┐
                   │  MySQL 8(7 张业务表)                 │
                   └─────────────────────────────────────┘

  微信小程序 ──────────────────────► 同一套 /api/v1/** 接口
```

### 2.2 设计原则

**原则一:三端共用一套后端,接口即契约。**
前台接口(`/api/v1/**`)与后台接口(`/api/admin/**`)在 controller 包层面物理隔离,统一 `Result{code, message, data}` 返回包装与 `PageResult{list, total, totalPages, hasNext}` 分页模型。三端各自维护一层 API 客户端,但 URL 完全一致——"一处维护、处处生效"。

**原则二:双语能力前置到数据层,而非运行时翻译。**
所有需要双语的业务表设计 `xx / xx_en` 双字段(如 `title / title_en`)。前端按当前语言取对应字段,中文环境零额外开销;英文内容由后台"录入即自动翻译"链路生产,不依赖运行时逐条翻译。

**原则三:一套 H5 代码,两种形态。**
不单独开发 PC 站,而是通过响应式断点(768/1024/1280/1440px)让同一套 Vue 组件在移动端呈现"底部 TabBar 形态"、在 PC 端呈现"左侧 SideNav 形态"。移动端优先、渐进增强。

**原则四:低配服务器约束下,"能不占内存就不占"。**
所有列表一律服务端分页(单页上限 20)、图片上传即压缩、热点数据 Redis 缓存、连接池按实际规格收缩、构建产物分包。性能是架构约束而非后期补丁。

### 2.3 技术选型理由

| 选型 | 理由 |
| --- | --- |
| Spring Boot 3 + MyBatis-Plus | 快速交付、逻辑删除/分页插件开箱即用,适合中小规模商业项目 |
| Redis(Spring Cache 注解) | 用注解声明式缓存替代手写缓存逻辑,业务代码零侵入 |
| Vue 3 `<script setup>` + Vite | 组合式 API 开发效率高,构建分包/自动导入开箱即用 |
| 原生微信小程序 | 页面与 H5 一一对应,避免引入 uni-app 等框架的额外心智与体积 |
| 百度翻译开放 API | 免部署、按量计费,后台配置化(appid/secret 存数据库,可随时更换) |

## 三、数据库设计

### 3.1 表结构总览(7 张表)

| 表名 | 用途 | 关键字段 |
| --- | --- | --- |
| `clothing_style` | 服装风格(男/女分离) | `style_name / style_name_en`、`clothes_gender(1男/2女)`、`sort_order` |
| `color_category` | 色卡分类(黑/白/蓝/紫…) | `category_name / category_name_en`、`category_code` |
| `color_card` | 色卡详情 | `card_name / card_name_en`、`card_image`、`category_id`、`product_id`(可空=独立色卡)、`is_featured` |
| `clothing_product` | 服装商品 | `title / title_en`、`cover`、`main_picture`(逗号分隔多图)、`description / description_en`、`clothes_gender`、`style_id`、`used_price/now_price`(分)、`total_num/rest_num`、`is_on/is_hot/is_new/is_custom` |
| `banner` | 首页轮播图 | `image_url`、`link_url`(站内路由或外链)、`position` |
| `yunyu_global_settings` | 系统全局配置(KV) | `setting_key`(唯一)、`setting_value`、`setting_group` |
| `admin_users` | 后台管理员 | `username`、`password`(BCrypt)、`last_login_time/ip` |

### 3.2 通用设计规范

**1) 全表三件套:** 每张业务表都有 `is_deleted`(逻辑删除,MyBatis-Plus 全局配置)、`create_time`(默认当前时间)、`update_time`(ON UPDATE 自动更新)。逻辑删除保证数据可追溯、可恢复,对运营类系统至关重要。

**2) 双语字段成对出现:** `xx / xx_en` 一一对应,英文列可空(未翻译时前端回退中文)。这是"双语前置到数据层"落地的根基。

**3) 索引与查询对齐:** 每个筛选维度都有对应索引——`clothing_product` 按 `gender/style_id/is_on/is_hot/is_new/is_custom` 建 6 个单列索引,与接口筛选条件一一对应;`color_card` 按 `category_id/product_id/is_featured` 建索引。

**4) 价格单位用"分"存储整数:** `used_price / now_price` 为 int(单位分),避免浮点误差,展示层除以 100 格式化。

**5) 可扩展的 KV 配置表:** 翻译 API 的 appid/secret 等运行时敏感配置不写死在代码/配置文件,存在 `yunyu_global_settings` 表,后台可改、Redis 缓存、修改即全量失效——替换翻译服务商无需发版。

### 3.3 数据迁移经验

旧版系统存在"一张 base_setting 表承载多种类型数据"(type=3 风格、type=4 色卡分类)的历史包袱。迁移策略:

- 按业务语义拆表:风格 → `clothing_style`,色卡分类 → `color_category`,色卡 → `color_card`(替代原 `product_color`);
- 迁移脚本保留数据血缘注释(如"从原 system_base_setting type=3 迁移"),便于追溯;
- 提供精简版 SQL(实际使用表)与全量版 SQL 双份,分别服务交付演示与正式环境。

## 四、后端设计

### 4.1 分层结构

```
controller
├── api/   前台接口(H5/小程序共用):product、color-card、style、banner、file、translate
└── admin/ 后台管理接口:auth、product、style、color-card、color-category、banner、global-settings、statistics、upload
service(+ impl)  →  业务逻辑
mapper           →  MyBatis-Plus 数据访问
entity / dto / vo → 数据模型三层分离(实体 / 入参 / 出参)
common
├── result       →  Result 统一返回、ErrorCode 错误码
├── exception    →  BusinessException + 全局异常处理器
└── utils        →  I18nHelper、ImageUrlHelper
config           →  MyBatisPlusConfig、RedisConfig、WebMvcConfig、AuthInterceptor
storage          →  图片压缩(ImageCompressor)
```

### 4.2 接口规范

**统一返回体:**

```json
{ "code": 200, "message": "success", "data": { ... } }
```

错误码集中在 `ErrorCode` 枚举(商品不存在、上传失败、认证失败等),`GlobalExceptionHandler` 统一捕获 `BusinessException` 与未知异常,保证任何错误路径都返回结构化 JSON 而非裸堆栈。

**分页模型:** 列表接口统一返回 `PageResult{list, total, totalPages, hasNext}`,前端据此渲染"上一页/下一页/跳页"。

**查询聚合:** 商品列表用 `ProductQueryDTO` 聚合 keyword / gender / styleId / isHot / isNew / isCustom / page / size 等全部筛选条件,一个 `queryProductList` 方法服务所有列表页(男装、女装、热门、新品、定制、搜索),避免每页一套查询。

### 4.3 认证设计(后台)

- **密码:** BCrypt 哈希存储(非对称盐),绝不存明文;
- **Token:** 自研无状态 Token——Base64Url 编码 `过期时间|userId|username|role|HMAC-SHA256签名`;服务端不存 session,校验时验签 + 查库确认账号未被禁用,24 小时过期;
- **拦截器:** `AuthInterceptor` 拦截 `/api/admin/**`,放行 OPTIONS 预检,401 时返回统一 JSON;登录接口记录客户端 IP(支持 X-Forwarded-For 透传)与最后登录时间。

### 4.4 缓存设计

| 缓存域 | key | 失效策略 | 说明 |
| --- | --- | --- | --- |
| 商品详情 | `product:detail:{id}` | 后台增删改 `@CacheEvict(allEntries)` | 详情组装含 2 次查询 + 关联色卡,缓存收益最高 |
| 翻译结果 | `translate:{text}:{from}:{to}` | TTL 到期 | 防止同一文案重复调用第三方翻译(计费) |
| 全局配置 | `globalSettings:{key}` | 配置修改全量失效 | 敏感配置读取高频 |
| 统计趋势 | `statistics:trend:{gender}:{days}` | TTL 到期 | 仪表盘按天统计,缓存一天无妨 |

缓存全部走 Spring Cache 注解,业务代码零侵入;Redis 通过 `application-{env}.yml` 多环境区分(dev 本机 / prod 服务器)。

### 4.5 图片处理链路

**上传(后台):** 校验(大小 ≤20MB、ContentType 为 image/*、扩展名白名单 jpg/jpeg/png/gif/webp)→ UUID 重命名 → Thumbnailator 压缩生成 3 个版本(original/large 复用、medium、thumbnail)→ 按 type 分目录落盘 `./uploads/{type}/{uuid}_medium.jpg`。

**回显(前台):** 前端拿到的图片地址统一走 `ImageUrlHelper.toUrl`——已带 http(s) 前缀的透传,相对路径补 `/api/file/get/` 前缀,由 `ApiFileController` 静态回源磁盘文件。**存储相对路径、展示时补全**,这是图片 URL 设计的核心决策(详见踩坑记录)。

### 4.6 翻译服务

- 后台录入中文后,前端 800ms 防抖调用 `/api/v1/translate`(POST 多行);
- 后端逐行调用百度翻译(按 `\n` 拆行、逐行翻译后重组,保证多行商品描述格式不丢);
- 结果 Redis 缓存,重复文案零外部调用;API 未配置时优雅降级(返回空,前端保留中文)。

## 五、H5 前端设计

### 5.1 技术栈与工程化

Vue 3.4(`<script setup>`) + Vite 5 + vue-router 4 + vue-i18n + axios + SCSS。刻意不引入 UI 组件库与状态管理库——设计系统自建,状态由组合式函数(hooks)承担。

**Vite 工程化要点:**

- `unplugin-auto-import` 自动导入 vue/vue-router API,`unplugin-vue-components` 自动注册 `src/components` 下组件,零手动 import;
- SCSS `additionalData` 全局注入设计变量与 mixin,所有组件样式零 import 直接使用;
- 生产构建 `manualChunks` 拆分 vue-vendor / i18n,路由级懒加载,terser 压缩;
- 生产 base 为 `/h5/`(Nginx 子路径部署),开发环境 `/api` 代理到本地后端。

### 5.2 自建设计系统(液态玻璃风格)

没有用现成 UI 库,而是构建了一套**设计令牌(Design Token)+ mixin 体系**,这是本项目视觉一致性的根基:

- `_variables.scss`:色彩(男装冷色系 `#8BA6B8` / 女装暖色系 `#D4C4B6` 双性别区分)、渐变、玻璃拟态色、字体、间距、圆角、阴影、模糊、动效、断点、PC 布局变量,全部集中定义;
- `_mixins.scss`:断点 mixin(mobile/tablet/desktop/desktop-lg/wide)、`glass-surface/glass-card/glass-button/glass-input`(毛玻璃拟态)、`liquid-hover`(液态悬浮)、`shimmer`(微光扫过)、`responsive-grid(2,3,4)`(响应式网格)、`page-container`(移动端为底部 TabBar 预留空间)、`text-ellipsis`;
- 效果:毛玻璃背景 + 微光扫过 + 柔和阴影,契合服装品牌"高级感"调性;换肤只需改 token,全站生效。

### 5.3 响应式双形态架构

`useResponsive` hook 监听窗口宽度,产出 `isMobile / isTablet / isDesktop / isDesktopLg`;`App.vue` 据此切换布局骨架:

| 形态 | 移动端(<768px) | PC 端(≥768px) |
| --- | --- | --- |
| 导航 | 底部胶囊悬浮 TabBar(6 项) | 左侧可折叠 SideNav(240px ⇄ 72px) |
| 网格 | 商品 2 列 / 色卡 3 列 | 商品 4 列 / 色卡 6 列,内容居中 1200px |
| 交互 | touch 手势 + active 缩放 | hover 动效 + 卡片悬浮 |
| 搜索 | NavBar 搜索模式 | 顶部居中搜索条 |

组件通过 `isDesktop` prop + SCSS `@include desktop` 双通道响应,一套代码两种体验。

### 5.4 路由与页面(8 页)

```
/                  Home          首页:搜索 + 新品推荐 + 热门色卡
/women | /men      Women/MenList 列表:风格筛选 + 服务端分页 + 搜索
/color-cards       ColorCards    色卡:分类 Tab + 分页 + 搜索
/custom            CustomList    高端定制列表
/new               NewList       新品上市列表
/product/:id       ProductDetail 商品详情:轮播 + 色卡联动 + 描述格式化
/color-card/:id    ColorCardDetail 色卡详情
```

**列表页统一模式(四个列表页共享):** 骨架屏加载 → 服务端分页(page/size) → 空状态 → 跳页输入;搜索 300ms 防抖;进入详情前把页码/筛选写入 `sessionStorage`,返回列表自动恢复,形成"原生 App 感"。

**商品详情页(复杂度最高):**

- 图片轮播:手势滑动(阈值 50px)+ 3s 自动播放 + 圆点指示器,触屏与鼠标事件兼容;
- 色卡联动:详情接口返回关联色卡列表,点击 swatch 切换选中色卡,联动展示色卡详情卡片并可跳转色卡页;
- 描述富文本:多行描述按格式智能分块(`细节描述:` 标题 / `key: value` 键值对 / `· 列表项` / 普通行),先 `escapeHtml` 再注入 HTML,兼顾排版与 XSS 安全。

### 5.5 双语实现(H5 侧)

- **前端文案:** vue-i18n,zh-CN/en-US 双语言包;`localStorage('boshark-lang')` 记忆选择,首次访问弹出玻璃风格语言选择浮层,可跳过;
- **数据内容:** `useLocalized` hook 封装 `localizedTitle / localizedStyleName / localizedCardName / localizedCategoryName / localizedDescription`——英文环境优先取 `*En` 字段,回退中文;
- **请求协商:** axios 请求拦截器自动携带 `Accept-Language` 头,后端消息 i18n 同步支持(ResourceBundle)。

### 5.6 搜索设计

- 首页:防抖 500ms,`Promise.allSettled` **并行**调商品搜索 + 色卡搜索,任一失败不影响另一个结果展示;
- 列表页:防抖 300ms 走服务端搜索接口(带分页),搜索态与浏览态无缝切换(清空关键词自动回到列表)。

## 六、PC 管理后台设计

### 6.1 技术栈与布局

Vue 3 + Element Plus + ECharts + Pinia + axios。路由为「登录页 /login」+「布局 /(layout)」两段式:`router.beforeEach` 全局守卫校验 `localStorage('admin_token')`,未登录跳登录页并携带 redirect 回跳;401 响应由 axios 拦截器统一清除 token 并踢回登录。

### 6.2 功能菜单(7 项)

| 菜单 | 技术要点 |
| --- | --- |
| 首页仪表盘 | ECharts 折线图展示商品趋势(总/新品/热门/定制/上架五条曲线,按天),数据来自统计接口 |
| 商品管理 | 搜索/性别/风格/特色(热门·新品·定制)多条件筛选 + 分页表格 + 新增/编辑对话框 |
| 男装风格 / 女装风格 | 按性别维护风格标签,前台 StyleTabs 实时生效 |
| 色卡分类 / 色卡管理 | 分类维护 + 色卡名称(中英)/图片/推荐标记/关联商品 |
| 轮播图管理 | 首页轮播图增删改 |

### 6.3 商品管理表单(核心交互)

- **中英双字段同屏:** 中文标题/描述输入框 + 英文标题/描述只读框并排;
- **自动翻译:** `watch` 中文输入,800ms 防抖调 `/v1/translate` 自动回填英文框——运营人员无需懂英文即可维护双语商品;
- **图片上传双通道:** 封面支持"粘贴 URL 或上传"(上传返回 medium 版 URL 回填);详情图多图上传,拼逗号分隔字符串存储,支持预览与逐张删除;
- **价格单位约定:** 表单按"分"录入(el-input-number step=100),表格展示 `/100` 转元并显示划线原价;
- **特色开关:** 热门/新品/定制用 Switch(1/0),与前台列表筛选一一对应。

## 七、微信小程序适配

### 7.1 统一与差异策略

小程序 8 个页面与 H5 一一对应,复用同一套后端接口,但落地时有几处关键差异处理:

| 维度 | H5 | 小程序 | 原因 |
| --- | --- | --- | --- |
| 请求路径 | `/v1/product/hot`(相对,Vite 代理) | `/api/v1/product/hot`(完整路径) | 小程序 baseUrl 是完整域名,无代理层 |
| 图片 URL | 后端已补全(http 前缀) | `fixImageUrl` 二次补全相对路径 | 小程序 `<image>` 组件必须绝对地址 |
| 搜索 | 服务端搜索接口 | 首页**客户端本地过滤**(加载 20+20 商品 + 100 色卡后前端 filter) | 小程序首批数据量小,本地过滤零延迟 |
| 轮播图 | H5 已改为新品推荐模块 | 小程序**保留轮播图**(swiper + linkUrl 路由映射) | 两端产品决策不同步的客观差异 |
| TabBar | 6 项(含新品) | 5 项(新品通过轮播入口) | 小程序 tabBar 数量/自定义约束 |
| 导航 | vue-router | `navigateTo / switchTab / navigateBack` | 平台 API 差异 |
| 双语 | vue-i18n + useLocalized | 数据字段直接取(无 i18n 依赖) | 小程序首版聚焦中文 |

### 7.2 典型页面实现(首页)

`onLoad` 用 `Promise.allSettled` 并行拉取轮播图、热门、男装、女装、色卡 5 路数据;轮播图 `linkUrl` 做路由映射(`/new` → navigateTo 新品页、`/custom` → switchTab 定制页、外链 → webview);`onShow` 同步自定义 tabBar 选中态。

### 7.3 通用工具沉淀

`utils/request.js` 统一封装:`Promise` 化 `wx.request`、`code===200/0` 判定、失败 toast、以及 `fixImageUrl / fixProductImages / fixColorCardImages / fixBannerImages` 一组图片补全函数——一处适配,全端生效。

## 八、性能优化与落地

### 8.1 约束背景

部署在 **2 核 4GB** 云服务器,规划支撑上千商品、4GB+ 图片。上线前对全链路做了一次"性能体检",发现一批如果不处理就会在数据量上来后直接击穿服务器的问题。

### 8.2 问题清单(体检结果)

| # | 问题 | 严重度 |
| --- | --- | --- |
| 1 | 男装/女装接口一次返回 1000 条商品,客户端再分页 | 🔴 数据量上来后 OOM |
| 2 | 首页挂载并行发 5 个请求,其中 2 个拉全量 | 🔴 首屏慢 + 服务器压力 |
| 3 | 色卡页一次拉 1000 条后客户端过滤 | 🔴 全量加载浪费 |
| 4 | Druid 连接池 initial=10 / max=50 | 🔴 连接池内存 50-250MB |
| 5 | Redis 连接池 max-active=50 | 🔴 远超实际需要 |
| 6 | 图片压缩生成 5 个版本 | 🔴 4GB 图片膨胀至 15-20GB 磁盘 |
| 7 | 商品详情 3 次 DB 查询 | 🟡 可合并 |
| 8 | 翻译无缓存,重复调第三方 | 🟡 浪费计费 |
| 9 | 无 gzip、Vite 单 chunk、未用依赖(Pinia/swiper) | 🟡 响应/首屏慢 |

### 8.3 改造落地

**后端:**

- 列表接口全部改为服务端分页(page/size,单页上限 20),Mapper/Service/Controller 三层同步删除全量查询方法——这是收益最大的改造;
- Druid 降为 initial=5/max=20,Redis 连接池同步收缩,把内存让给业务;
- 图片压缩 5 版 → 3 版(original/large 合并复用、medium、thumbnail),磁盘压力减半;
- 翻译结果、商品详情、统计趋势、全局配置全部走 Redis 缓存;
- 开启 gzip 响应压缩。

**前端:**

- 首页 5 个并行全量请求 → 轻量分页请求 + `Promise.allSettled` 并行(后续迭代进一步精简至 2 个);
- 四个列表页从"全量加载客户端分页"改为服务端分页 + 搜索接口;
- Vite `manualChunks` 拆分 vue-vendor/i18n + 路由懒加载;移除未使用的 Pinia、swiper 依赖(依赖瘦身本身就是性能优化)。

### 8.4 结果对比

| 维度 | 优化前 | 优化后 |
| --- | --- | --- |
| 单次列表数据量 | 最多 1000 条 | 每页 ≤ 20 |
| 首页请求数 | 5 个(含全量) | 2-3 个轻量分页请求 |
| 连接池内存 | 50-250MB | 显著收缩 |
| 图片存储 | 5 版本 | 3 版本 |
| 第三方翻译调用 | 重复调用 | 缓存命中零调用 |
| 首屏 JS | 单一大 chunk | 分包 + 懒加载 |

## 九、部署与运维

### 9.1 部署架构

```
用户 → 域名(备案) → Nginx
                      ├── /h5/*        → H5 静态资源(Vue build 产物)
                      ├── /api/*       → 反向代理到后端 8080
                      └── /            → 管理后台(或独立子路径)
后端 → MySQL(本机) + Redis(本机) + ./uploads 图片目录
```

### 9.2 关键实践

- **子路径部署:** H5 构建 `base: '/h5/'`,Vue Router 用 `createWebHistory(import.meta.env.BASE_URL)`,Nginx 按路径分发——三端共存于同一域名;
- **多环境配置:** `application-{dev,min,prod}.yml` 三套——dev 本机调试、min 精简配置、prod 生产规格(连接池、缓存 TTL 按服务器实际能力调整);
- **图片目录:** `app.upload.path=./uploads` 独立目录,上传文件与代码分离,便于备份与迁移;
- **上传大小:** Spring 端 multipart 20MB 限制与 Nginx `client_max_body_size` 配套,避免网关层截断。

### 9.3 运维注意

- 翻译 API 密钥存数据库配置表,后台可改、无需发版;
- 管理员登录记录 IP 与最后登录时间,可审计;
- 上线后按真实反馈持续迭代(新品模块、高定转换、翻译修复等),每个改动保留 git 提交记录可追溯。

## 十、踩坑记录(真实教训)

### 坑 1:全量加载的隐性 OOM 炸弹
**现象:** 列表接口"图省事"一次返回 1000 条,本地数据量小时毫无感知。
**根因:** 商品上千后,每次请求全量加载到内存,2 核 4GB 直接 OOM;首页还同时发多个全量请求。
**解决:** 服务端分页 + 单页上限 20 + 首页轻量化改造。
**沉淀:** 列表接口**必须**服务端分页,单页上限是硬约束,不能靠客户端兜底。

### 坑 2:图片 URL 相对路径在跨端不一致
**现象:** 后台存了 `uploads/xxx.jpg`,H5 正常显示,小程序一片空白。
**根因:** 小程序 `<image>` 组件强制要求绝对地址,相对路径不可用;不同端对 URL 的处理约定不统一。
**解决:** 后端 `ImageUrlHelper.toUrl` 统一在**出参时**补全相对路径为 `/api/file/get/` 前缀;小程序侧再兜底 `fixImageUrl` 补域名。约定:**存储相对路径、出参补全、前端兜底**。
**沉淀:** 图片 URL 的"相对/绝对"约定要在架构层面定死,前端各端各兜底一次。

### 坑 3:翻译服务"无状态"导致重复计费
**现象:** 后台每改一次标题就调一次第三方翻译,相同文案反复翻译。
**根因:** 翻译接口无缓存,且"逐字符调用"没有批处理。
**解决:** Redis 缓存 `translate:{text}:{from}:{to}` + 前端 800ms 防抖 + 多行文本按行拆分重组。
**沉淀:** 任何第三方付费 API 调用前,先问"能不能缓存、能不能防抖、能不能合并"。

### 坑 4:多行商品描述翻译后格式丢失
**现象:** 商品描述是多行结构化文本(标题行/键值对/列表项),整段一次性翻译后排版全乱。
**根因:** 翻译 API 对换行、空行的处理与原文本不一致。
**解决:** 按 `\n` 拆行逐行翻译再重组,前端渲染时再按行格式智能分块(`细节描述:`/`key: value`/`· item`),escapeHtml 防 XSS。
**沉淀:** 翻译/处理"结构化文本"时,先拆结构、逐块处理、再重组,不要整段盲处理。

### 坑 5:轮播图业务被"新品上市"替代后,接口与页面脱节
**现象:** 迭代中把 H5 首页轮播图改成了新品推荐模块,但 banner 接口、后台轮播图菜单、小程序轮播图仍在运行。
**根因:** 产品决策变更时,只改了 H5 页面,未同步清理其他端与接口。
**解决:** 保留后台轮播图管理能力(可随时切换回轮播模式),小程序继续用轮播图,前端 API 层保留 `bannerApi`。
**沉淀:** 功能迭代时要做"跨端影响分析"——改一个端,确认其他端与接口是否同步。

### 坑 6:价格单位不一致(元/分)
**现象:** 后台按"元"录入,前端直接展示出"1"而非"1.00",或出现浮点误差。
**根因:** 价格单位约定(元 vs 分)没有文档化。
**解决:** 统一按"分"存 int,后台表单 step=100 录入,表格 `/100` 展示元。
**沉淀:** 金额、时间等"单位敏感"字段,单位约定必须写入接口契约。

### 坑 7:跨域与预检(OPTIONS)
**现象:** 小程序/H5 直连后端时偶发跨域失败。
**根因:** 前后端分离 + 自定义 Header(Authorization、Accept-Language)触发 CORS 预检。
**解决:** 后端 `WebMvcConfig` 统一配置 CORS(`allowedOriginPatterns("*")` + OPTIONS 放行);生产环境由 Nginx 同源代理规避。
**沉淀:** CORS 配置要覆盖"自定义请求头 + 预检放行",同时尽量用网关同源代理减少跨域面。

### 坑 8:数据迁移中的"历史包袱表"
**现象:** 旧库一张 `base_setting` 表混合存放多种业务数据(type 区分),直接沿用无法满足新查询。
**根因:** 旧系统设计时用"配置表装一切"。
**解决:** 按业务语义拆分为风格/色卡分类/色卡三张表,迁移脚本注明数据来源,提供精简/全量双份 SQL。
**沉淀:** 迁移不是"搬数据",是"重构数据模型"——拆表、清洗、追溯三件事缺一不可。

## 十一、通用技术沉淀(可复用到下一个项目)

### 11.1 可复用设计模式

| 模式 | 落地位置 | 复用价值 |
| --- | --- | --- |
| 统一返回体 + 全局异常 | `Result` + `ErrorCode` + `GlobalExceptionHandler` | 所有接口错误路径结构化,前端拦截器一次写死 |
| DTO 聚合查询 | `ProductQueryDTO` + 单方法查询 | 一个查询入口服务 N 个列表页,避免接口爆炸 |
| 声明式缓存 | Spring Cache 注解 + Redis | 业务零侵入加缓存,key 策略集中管理 |
| 双语字段前置 | `xx / xx_en` + `useLocalized` | 双语系统不需要运行时翻译引擎 |
| 设计令牌系统 | SCSS variables + mixins | 无 UI 库也能全站视觉统一,换肤改变量 |
| 组合式 Hook 抽离 | `useResponsive / useLocalized` | 响应式、本地化等横切逻辑一次封装处处用 |
| 防抖 + 并行容错 | 搜索防抖 + `Promise.allSettled` | 高频输入与多路请求的标准解法 |
| 列表状态记忆 | sessionStorage 页码/筛选 | 列表→详情→返回,体验接近原生 App |

### 11.2 工程习惯沉淀

1. **低配服务器是常态:** 先按"最差硬件"做性能设计(分页上限、连接池收缩、图片压缩),再谈功能;
2. **第三方付费 API 三问:** 能不能缓存、能不能防抖、能不能批处理;
3. **接口契约文档化:** 价格单位、图片 URL 约定、分页模型,写进文档比写进代码更抗迭代;
4. **跨端影响分析:** 产品改一个端,必须检查其他端与接口是否同步;
5. **双份 SQL 交付:** 精简版(演示/理解)+ 全量版(生产),交付体验更好。

## 十二、经验总结与反思

### 12.1 做得对的事

- **"三端一后端 + 接口即契约"的架构决策**,让小程序/H5 双端开发成本接近"一套页面抄两遍",后续功能迭代(H5 新品、高定)一次开发多处生效;
- **双语前置到数据层**,避免运行时翻译的性能与成本问题,运营链路(后台自动翻译)闭环;
- **移动端优先的响应式策略**,一套 H5 代码同时交付手机与 PC,交付物数量减半;
- **性能优化做在数据量上来之前**,2 核 4GB 服务器至今稳定运行,没有出现 OOM 事故。

### 12.2 可以做得更好的地方

| 反思点 | 现状 | 改进方向 |
| --- | --- | --- |
| 鉴权 | 自研 HMAC Token(简单够用) | 可替换为成熟 JWT 库 + Refresh Token,支持吊销 |
| 翻译降级 | 未配置时返回空,前端保留中文 | 可增加"翻译失败告警 + 重试队列" |
| 搜索 | 列表页走服务端,首页小程序端本地过滤 | 统一服务端搜索,加入拼音/同义词 |
| 前端状态 | 无状态管理库,靠 props/emit + hooks | 页面交互复杂度上升后可引入 Pinia |
| 图片处理 | 磁盘存储 + 三版本压缩 | 可上对象存储 + CDN,进一步降低服务器 IO |
| 测试 | 以手工回归为主 | 补充接口自动化测试与前端关键路径 E2E |
| 日志与监控 | 日志文件 + 人工排查 | 接入集中日志与告警,上线后主动发现问题 |

### 12.3 一句话总结

> 这是一个"**小团队、低配服务器、商业交付**"约束下的完整全栈项目:架构上做减法(三端一后端、双语前置、响应式一套代码),工程上做防守(分页硬上限、缓存先行、图片压缩、双份 SQL),交付上做闭环(需求→设计→开发→优化→迁移→部署→迭代)。它证明了:**在资源受限的条件下,良好的架构决策与工程习惯,比堆技术栈更能决定项目的成败。**
