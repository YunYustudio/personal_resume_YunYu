**关键点**

- 微信支付只与后端交互（小程序拉起 JSAPI 所需的 `payParams` 由后端用商户号签名生成），密钥不落地前端。

## 五、关键功能与技术亮点（面试加分项）

### 1. 订单状态机（非连续值设计）
- 状态：`0待付款 → 1待发货 →[接单]→ 4配送中 → 2待收货 → 3已完成 / 9已取消`。
- **为什么值不连续（0/1/2/4/3/9）**：业务语义是按"生命周期阶段"而非"数字大小"排列的，`4配送中` 插在 `1待发货` 和 `2待收货` 之间，所以刻意不连续。
- **原子转移**：所有状态变更走 `UPDATE ... SET status=to WHERE status=from AND id=?`，靠数据库行锁保证不会出现"从错误状态跳转"，且天然幂等（已经跳转过的单，WHERE 不匹配 → 影响行数 0 → 直接跳过）。
- **并发防丢失更新**：`order_info` 加 `version` 列 + MyBatis-Plus 乐观锁插件，后台改单与支付回调并发时不会把已支付订单覆盖回未支付。

### 2. 支付全链路（幂等 + 三链路合一）
- 真实微信 JSAPI + **演示支付开关**（`sys_config.pay_demo_enabled`）：开=后端本地直接走 `handlePaySuccess` 并打 `MOCK_` 前缀，不调真实微信；关=走真实 `refundV3`/支付。
- **幂等保证**：支付成功处理 `handlePaySuccess` 同时被**真实回调、主动查单（轮询）、演示支付**三条链路调用，靠订单状态守卫（`WHERE status=待付款`）保证只生效一次。
- 退款同理：微信退款回调 `updateStatus(PROCESSING→SUCCESS)` 带状态守卫，重复回调不重复回滚。

### 3. 退款 / 售后体系（本项目最复杂、最能体现业务理解）
- **仅退款（不退货）作为默认高频模式**：生鲜收到后部分变质/缺斤少两，只退钱不退实物——所以把"仅退款"设为默认，覆盖待发货/待收货/已完成全阶段。
- **部分退款**：待收货/已完成支持按商品勾选 + 逐项正确金额，后端逐明细校验（存在 / >0 / ≤ 单价×数量 / 总额 ≤ 实付）并**累计超额校验**（读 `refund_order_item` 已成功退款金额，防多次部分退款超总额）。
- **自动同意**：商家 >24h 不处理用户退款 → 定时任务 `RefundAutoAgreeTask` 自动同意；仅退款 + **退款额 ≤ 200 元**（`refund_auto_agree_max_amount` 可配）才自动退，超额交人工。
- **一键取消原路退款**：已支付 + 待发货，用户点"取消订单"立即原路退款（演示模式本地闭环 / 真实微信发起），分钟级到账，不走售后流程。
- **逐项回滚**：退款成功按 `refund_order_item` 逐明细回滚库存与销量（修复了"整单回滚"在部分退款下的 bug）。

### 4. 购物车清空时机设计
- 在**支付成功**时按 `order_info.source_cart_ids` 精准清空对应条目，而非"下单时"清空。原因：避免未付款 / 超时取消时误删购物车（用户仍可重新下单），语义与"完成支付后才与购物车一致"对齐。

### 5. 定时任务三件套（系统自动化履约）
- `AutoConfirmReceiveTask`：已送达后 **12h** 客户未手动确认 → 系统自动确认收货（锚点 `deliveryTime`）。
- `RefundAutoAgreeTask`：用户发起退款 **24h** 商家未处理 → 自动同意（仅退款 + ≤200 元）。
- `cancelTimeoutOrders`：未支付订单 **30 分钟** 超时自动取消。
- 全部用 **Redisson 分布式锁**，多实例部署不会重复执行。

### 6. 地址模块：真实行政区划数据
- 省市区选择器数据源从占位数据替换为**民政部标准全量真实数据**（开源项目 modood/Administrative-divisions-of-China），三级结构 `provinceList / cityMap / districtMap`，并因主包体积告警把大文件 `region.ts` 从 `utils/` 迁入 `pages/address/` 分包。

### 7. 密钥安全红线（工程素养体现）
- 微信支付 APIv3Key / COS SecretKey 等**一律不进提交的 yml、不进 Gitee**，存 `sys_config` 表（AES 密文），yml 只放 `${...:}` 占位兜底。

## 六、技术难点 & 我怎么解的（面试讲故事用 · STAR 法）

> 面试官最爱问"你遇到最难的问题是什么"。下面每个都是真实发生过、你独立定位并解决的，按 STAR（情境-任务-行动-结果）准备即可。

### 案例 1：下单 INSERT 报 `Field 'id' doesn't have a default value`
- **现象**：`order_info` / `cart` / `user_address` 等多张表 INSERT 失败，报主键无默认值。
- **根因**：活库发生了**结构漂移**——建表 DDL 里 `id` 是 `AUTO_INCREMENT`，但库里被改丢了，MyBatis-Plus 的 `IdType.AUTO` 生成 INSERT 省略 id 列，依赖 DB 自增，库无自增即拒插。
- **行动**：先单表 `ALTER` 修，后发现是系统性漂移（5 张表都中招），写成**全库 id 自增补齐脚本**（SELECT 出所有"id 是主键、整型、未自增"的表，生成 ALTER 批量修），并特意避开 Navicat 对 `DELIMITER + 存储过程` 的坑，改用纯 SELECT 生成 SQL 文本。
- **结果**：一次性根治，不动数据，后续不再逐个撞坑。

### 案例 2：退款成功但库存没回滚（库存泄漏）
- **现象**：代码审查发现 `handleRefundSuccess`（退款成功）只置状态，**没把下单预扣的库存加回去**，退款后库存永久少。
- **行动**：补 `rollbackStockByOrderId(orderId)`，并在部分退款改造时进一步改为**按 `refund_order_item` 逐明细回滚**库存与销量。
- **结果**：整单退 / 部分退都不会泄漏库存，销量也不会出现负数。

### 案例 3：并发丢失更新（乐观锁）
- **现象**：支付回调把订单置"已支付"的同时，后台若改备注/改价，可能把"已支付"覆盖回"未支付"。
- **行动**：`order_info` 加 `version` 列 + 注册 `OptimisticLockerInnerInterceptor`，所有更新带版本号，冲突则抛异常由调用方重试。
- **结果**：支付状态与后台操作并发安全。

### 案例 4：发货竞态关闭在途退款（资损防护）
- **现象**：原"发货时关闭待发货在途退款"逻辑没排除已提交微信的退款单，会导致"钱已退 + 货又发出 + 状态永久错乱"。
- **行动**：关闭前加守卫——**在途退款（`out_refund_no` 非空）则拒绝发货**，只关未提交微信的退款单。
- **结果**：退款与发货两个动作互斥，杜绝钱货两失。

### 案例 5：立即购买清单空白
- **现象**：商品详情"立即购买"→ 确认订单页商品清单空白。
- **根因**：`loadBuyNow` 写死 `fetchGoodsDetail(0)`（占位 spuId），且参数语义错配（传的是 skuId 当 spuId 查）。
- **行动**：跳转时补传 `buyNowSpuId`，确认页按 spuId 拉详情再用 `skuId` 反查选中 SKU，组装真实 `OrderItemVO`。
- **结果**：立即购买与购物车两条结算路径表现一致。

### 案例 6：后台点订单详情误退出登录
- **现象**：PC 后台点任意订单"详情"直接登出。
- **根因**：后台 `orderDetail` 复用了 C 端"按当前登录用户隔离"的详情方法，C 端方法首行取 `StpUserUtil` 登录态，但管理员用 `StpAdminUtil` 登录、无 C 端登录态 → 抛未登录异常 → 前端判定 401 登出。
- **行动**：把"取订单 + 权限校验"与"VO 组装"分离，后台只用组装部分（`buildDetailVO`），不复用带隔离的方法。
- **结果**：后台可正常看任意订单详情，C 端隔离逻辑不受影响。

## 七、面试官高频追问 & 标准答案（最重要部分）

### Q1：为什么订单状态值不是连续的（0/1/2/4/3/9）？
- **一句话**：状态值是按业务"生命周期阶段"语义排的，不是按数字大小，`4 配送中` 插在 `1 待发货` 和 `2 待收货` 之间，所以刻意不连续。
- **展开**：这样设计的好处是状态枚举可读性高；代价是**绝不能用 `status > 2` 这类范围比较**，必须显式枚举每个值。我在代码里所有判断都是 `== 具体值` 或 `IN (...)`。
- **加分**：正因为值不连续、且跳转必须走 `WHERE status=from` 的原子 UPDATE，所以状态机天然防错跳、防并发重复处理。

### Q2：支付怎么保证幂等？微信重复回调怎么办？
- **一句话**：支付成功处理 `handlePaySuccess` 被真实回调、主动查单、演示支付三条链路共用，靠订单状态守卫保证只生效一次。
- **展开**：`handlePaySuccess` 内部更新订单状态用 `WHERE status=待付款`，已支付过的单影响行数 0，直接跳过；退款回调 `updateStatus(PROCESSING→SUCCESS)` 同理带状态守卫。
- **加分**：支付还做了"主动查单"兜底（轮询微信确认支付结果），与回调共用同一成功处理逻辑，避免"回调丢失导致订单长期待付款"。

### Q3：退款怎么防止超退？部分退款怎么算？
- **一句话**：部分退款按商品明细逐项校验金额，并读 `refund_order_item` 已成功退款总额做累计超额校验，确保多次退款加起来不超过实付。
- **展开**：校验规则——每条明细退款额 >0 且 ≤ 该商品单价×数量；本次退款总额 ≤ 实付；累加历史成功退款后不超实付。`refund_status` 细化成 无/处理中/部分/整单，部分退款后订单主状态不变、仍可继续退剩余。
- **加分**：逐明细回滚库存与销量，整单退与部分退都不会泄漏或重复回滚。

### Q4：高并发下单 / 支付怎么处理？
- **一句话**：库存预扣用 `UPDATE stock=stock-num WHERE stock>=num`（原子、不超卖），订单更新用 `version` 乐观锁防并发丢失更新，状态机用 `WHERE status=from` 防错跳。
- **展开**：没有用粗暴的 `SELECT` 再 `UPDATE`，所有变更都下推到带条件的单条 UPDATE，靠数据库行锁保证原子性。
- **加分**：（若被追问更高并发）当前是演示/中小规模，单机 MySQL 足够；再往上会引入 Redis 预扣库存 + 消息队列削峰 + 分库分表，但核心思路不变——"变更下推到带条件的原子 UPDATE"。

### Q5：购物车为什么在支付成功时才清空，而不是下单时？
- **一句话**：避免用户未付款或超时取消时误删购物车，保证"完成支付后才与购物车一致"的语义。
- **展开**：`createOrder` 只把来源购物车 ID 记录到 `order_info.source_cart_ids`，真正的清空在 `handlePaySuccess` 里按具体 ID 精准逻辑删除；三支付链路（回调/查单/演示）共用，清空失败抛异常 → 整笔支付事务回滚 → 微信重试补齐，最终一致。
- **加分**：前端 `onShow` 改为每次都重新拉取购物车，解决"支付后 UI 仍显示已购商品"的缓存 bug。

### Q6：个人主体小程序怎么演示支付？（没有真实商户号）
- **一句话**：后端加了"模拟支付开关" `pay_demo_enabled`，开启时不调真实微信，本地直接走支付成功逻辑并打 `MOCK_` 前缀，把完整交易链路（下单→支付→退款）演示闭环。
- **展开**：演示开关与真实微信支付共用同一套 `handlePaySuccess` / `agreeRefund`，只是数据源不同；真正要收款需先办个体工商户营业执照 → 升级小程序主体 → 申请微信支付商户号。
- **加分**：演示数据用专用清理 SQL 定向删除（`MOCK_` 前缀），绝不 `TRUNCATE`，保证测试数据可追溯。

### Q7：密钥 / 密码怎么管理？
- **一句话**：任何真实密钥（微信支付 APIv3Key、COS SecretKey、商户号）一律不进提交的 yml、不进 Gitee，存 `sys_config` 表（AES 密文），yml 只放 `${...:}` 占位兜底。
- **加分**：证书落非公开目录且绝不做成 Nginx 静态资源；这是我给自己定的工程红线，整个项目提交历史里没有任何 `.pem` / 真实密钥。

### Q8：定时任务多实例怎么防重复执行？
- **一句话**：所有定时任务用 **Redisson 分布式锁**，多实例只有一个拿到锁的执行，避免重复扫描 / 重复自动确认收货 / 重复自动退款。
- **加分**：每个任务逐单 try/catch，单条失败不影响整体，下一轮重试，保证最终一致。

### Q9：微信支付部分退款，个体工商户商户支持吗？
- **一句话**：支持。个体工商户 = 普通商户，微信支付支持部分退款（单笔可分多次、每次 ≤ 订单金额、一年内可退），所有商户通用，不存在"个体户不支持部分退款"的限制。
- **加分**：真实约束只是——退款从可用余额/基本户扣（余额不足需充值）、同单多次退款间隔 1 分钟、超 1 年不可退。

### Q10：整个项目你怎么保证代码质量？
- **一句话**：每个功能写完我都会做一遍"生产级代码审查 + 业务闭环分析"，并把发现的问题火速修复，再同步更新开发文档。
- **展开**：例如退款模块我审查出"退款成功未回滚库存""并发丢失更新""发货竞态关闭在途退款""退款明细金额空白"等真实缺陷，全部修复；文档与代码同步维护（13 类开发文档 + 84 个接口清单）。
- **加分**：我把"结构漂移""乐观锁""幂等"这类坑都沉淀成了可重复执行的 SQL 脚本和文档，下一个环境直接复用。

## 九、项目复盘 & 可优化点（展示自我认知，反而是加分项）

**当前是演示/体验版，已知的边界：**
- 真实微信支付需办个体户执照升级主体，当前靠模拟支付开关演示。
- 部分设计（如自动时效写死为常量 12h/24h/30min）是为"简单可维护"刻意取舍，未做后台可配 UI。

**如果继续演进，我会做（体现技术广度）：**
- **分布式事务 / 最终一致**：当前退款回滚与支付用数据库本地事务 + 重试保证一致；更大规模会引入消息队列（退款事件异步化）+ 对账任务。
- **缓存**：热点商品 / 店铺配置 / 数据大屏指标加 Redis 缓存，降低 DB 压力。
- **可观测性**：接入日志聚合 + 监控告警（支付成功率、退款到账时效）。
- **CI/CD**：当前手动构建；可上流水线（构建 → 单测 → 部署）。
- **分库分表 / 读写分离**：订单域表随量大后可按用户/时间分片。

## 十、面试演练建议（怎么讲不翻车）

1. **先背熟"30 秒自我介绍"**（第一节），开场就定调"全栈 + 完整交易链路 + 自己解决真实问题"。
